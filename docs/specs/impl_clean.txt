1. Purpose, Scope and Definition of Done
This guide is the build manual for Phase 1 of Hurrykit: the image, audio and video converters. It assumes the decisions in the Product Vision Document and turns them into things a developer (or a coding agent) can build step by step. It is implementation only; strategy lives in the vision document.
In scope for Phase 1
The shared site shell: home page, three department hubs, tool pages, format pages, guides, trust and legal pages.
The tool registry that drives every page, hub, link and sitemap entry.
Three engines running in the browser: image (canvas and WebAssembly codecs), audio and video (FFmpeg compiled to WebAssembly).
About 59 conversion pages across image, audio and video, plus the hubs.
Basic analytics, error logging, SEO output and a test suite.
Free hosting and automated deployment.
Out of scope for Phase 1
Editing tools (compress, trim, crop and similar; Phase 2).
Exam-photo tools and Hindi text tools (Phase 3).
Accounts, payments, ads and any server-side processing.
A Hindi version of the site.
Fixed decisions carried in from the vision
Files are processed on the user's device and never uploaded.
No signup, no watermark.
Frontend is React only. The brand name is Hurrykit. The domain is not bought yet, so the build works on a free-host preview address and a configurable site URL.

2. Architecture Overview
Hurrykit Phase 1 is a static website plus three in-browser engines. There is no application server. Pages are built ahead of time into plain files; when a user opens a tool, the browser downloads the engine it needs and does the work locally.

How one conversion flows
The user opens /heic-to-jpg. The static page loads quickly with no engine code.
The user drops a file. The tool UI checks the type and size against the tool's rules in the registry.
The UI asks the engine factory for the engine named in the registry. The engine code loads on demand.
The engine runs in a Web Worker, reports progress, and returns a result as a file object in memory.
The UI shows the result with size and a download button. The user's file is never sent anywhere.
The result can be downloaded, previewed or shared, and is cleared from memory when the user leaves or clicks clear.

flowchart LR  U[User drops file] --> V[Validate type and size]  V --> F[Engine factory]  F -->|image| IE[Image engine worker]  F -->|audio/video| FE[FFmpeg engine worker]  IE --> R[Result blob in memory]  FE --> R  R --> D[Download button]  IE -. progress .-> UI[Progress bar]  FE -. progress .-> UI
Design rules
One template, one registry. Adding a conversion page means adding a record, not writing a page.
Engines are replaceable. The UI talks to an interface, so a library can be swapped without touching pages.
Heavy code loads only when needed. The home page and hubs load no engine.
Every engine runs in a worker so the page stays responsive and cancel works.
Nothing is stored server-side. Any history or recent files stay in the browser only.
Fail visibly. Every error path produces a message the user can act on.
What is deliberately not in Phase 1. No database, no authentication, no queue, no server functions for conversion. The only server-side pieces are static files and, later, small endpoints for error reports.

Conventions
File names: lower-case with hyphens for content, PascalCase for React components.
Imports: use path aliases (@/engines, @/registry).
One component, one job. Components that need engine code import it through the factory and never directly.
No engine imports in shared layout code. A check in CI fails if the home page bundle contains engine code.
Content and code are separate. Copy lives in content/, not inside components.
Environment variables are listed in a documented .env.example. The site URL and analytics IDs are variables so the domain can change later without code edits.
Branching. The main branch is always deployable. Work happens on short branches; every branch gets a preview deployment; merging runs the full test suite.

Generation rules
Pairs are generated, not typed. A department file lists the allowed (from, to) pairs and a few overrides; a function builds the records and fills defaults from the format table.
Validation at build time. Zod checks every record. The build fails on a missing format, a missing content file, a duplicate slug, a copy under the minimum word count or an unknown related ID.
Derived pages. The registry produces the hub lists, the related-tools lists, the format pages' "all conversions" lists, the sitemap and the site search index.
Status gates publishing. Only live records appear in navigation and the sitemap; ready and draft appear only in preview builds.
Content per record. Each tool record must reference a Markdown file with these fields: intro, why-people-convert, format-facts, tips-and-limits, and three to six FAQs.

7. Engine Abstraction and Workers
All conversion code sits behind one interface. The UI never knows whether a job is done by the canvas, a WebAssembly codec or FFmpeg.
The interface
export type JobInput = {  file: File;  toolId: string;  from: string;            // detected input format ID  to: string;              // target format ID  options: Record<string, string | number | boolean>;};export type JobProgress = { stage: 'loading-engine' | 'reading' | 'converting' | 'encoding' | 'finishing'; fraction: number; message?: string };export type JobResult = { blob: Blob; fileName: string; mime: string; bytes: number; notes?: string[] };export type JobError = { code: ErrorCode; message: string; detail?: string; recoverable: boolean };export interface Engine {  readonly id: 'image' | 'ffmpeg';  canHandle(input: JobInput): boolean;  prepare(onProgress?: (p: JobProgress) => void): Promise<void>;   // load code and warm up  run(input: JobInput, onProgress: (p: JobProgress) => void, signal: AbortSignal): Promise<JobResult>;  dispose(): void;                                                  // free memory, terminate worker}
Worker model
Each engine owns one dedicated Web Worker, created on first use.
The page talks to the worker through a small message protocol: prepare, run, cancel, progress, result, error.
Large data moves as transferable buffers, not copies, to avoid doubling memory.
Cancellation: for image jobs, the worker checks an abort flag between steps; for FFmpeg jobs, the worker is terminated and recreated, which is the reliable way to stop a running command.
One job at a time per engine. The queue runs files in sequence; parallelism is limited to protect low-end devices. The image engine may run two small jobs at once on devices with enough cores (see section 15).
Idle cleanup. After a period with no jobs, the worker is terminated to release memory. It reloads from cache on the next use.

Shared services
Format detection. Check the file's first bytes (magic numbers) and the extension; never trust the extension alone. A user who renames a PNG to JPG still gets a working conversion.
Output naming. Keep the original base name and change the extension (IMG_0012.HEIC becomes IMG_0012.jpg); add a number if a name repeats in a batch.
Progress. Normalise progress to a value from 0 to 1 across stages, with a time-remaining estimate once enough data exists.
Memory guard. Before a job, estimate memory needed from file size and type; warn or block above the device limit.
Feature detection. Check for the worker, WebAssembly, OffscreenCanvas and (for the multi-thread core) shared memory before offering a tool, with a clear fallback.
Factory. getEngine(id) returns a singleton, creating it on demand.
8. Image Engine
The image engine handles every still-image conversion in Phase 1. It decodes the input into pixels, optionally adjusts them, and encodes them into the target format.
Pipeline
Detect the real input format from the first bytes.
Decode to an ImageBitmap or raw RGBA pixels. Use the browser's decoder when it supports the format; use a WebAssembly decoder otherwise.
Adjust (only what the tool needs): fill a background colour when the target has no transparency, apply the EXIF orientation, and resize if the user chose a size.
Encode with the browser's canvas encoder for JPEG, PNG and (where supported) WebP, or with a WebAssembly encoder for formats and quality levels the browser cannot do well.
Return a Blob with the right MIME type and file name.

Shared image behaviours
Orientation. Respect EXIF orientation so phone photos are not rotated incorrectly. Browsers apply it when drawing to a canvas in current versions; verify with test files and add manual rotation if needed.
Colour and bit depth. Canvas works in 8-bit sRGB. Wide-gamut and 10-bit images (some iPhone photos) are converted to sRGB; mention this in the page copy.
Transparency. For formats without alpha (JPEG), fill the background white by default, with a colour picker option.
Metadata. Canvas encoding removes most metadata (EXIF, GPS). Say so on the page, since it also protects privacy. Offer a "keep metadata" option only if a library supports it reliably (later).
Quality option. One slider, default 90 for JPEG and WebP; for PNG a "smaller file" toggle only when a WebAssembly PNG optimiser is added.
Resize option. Optional: keep original, or limit the longest side.
Limits that matter
Canvas area. Browsers cap canvas size, and iOS Safari is strict (the commonly cited cap is about 16.7 million pixels, and lower memory devices can fail earlier) (verify on devices). Large photos (for example 48 or 108 megapixel phones) must be handled by downscaling to a safe size with a visible warning, or by tiling for WebAssembly paths.
Memory. A decoded image takes about 4 bytes per pixel. A 50-megapixel image is about 200 MB before encoding; the memory guard (section 15) uses this formula.
Speed. Use OffscreenCanvas inside the worker where available. Where it is not (older Safari), fall back to the main thread for small images and show a notice for large ones.
HEIC specifics
HEIC is the most requested conversion, so it gets the most testing: iPhone photos in both standard and high-efficiency settings, Live Photos (still part only), portrait mode photos with depth data, HDR (Dolby Vision) photos, and files from Samsung and other phones.
Convert in batches with a progress count, because people convert dozens of photos at once.
Offer "download all as ZIP" for three or more results (section 13).
Test checklist for every image tool
One small, one typical and one very large input.
Rotated (EXIF orientation 3, 6, 8) input.
Transparent input going to JPEG.
Greyscale and CMYK JPEG input.
A file with the wrong extension.
A corrupt file.
A batch of ten files.
9. Audio Engine
Audio conversion runs on FFmpeg compiled to WebAssembly (section 12 covers loading and hosting). The audio engine is a thin layer that builds the right command for each target format and reads the result.
Pipeline
Write the input file into FFmpeg's in-memory file system. For larger files, mount the file read-only so it is not copied (verify the mounting option in the chosen version).
Run a command built from the target format and the user's options.
Read the output file back, wrap it in a Blob and return it.
Delete the input and output from the virtual file system immediately.

Command patterns
# Any audio to MP3 (192 kbps)ffmpeg -i input.opus -vn -map_metadata 0 -c:a libmp3lame -b:a 192k output.mp3# Any audio to AAC in an M4A containerffmpeg -i input.wav -vn -c:a aac -b:a 192k -movflags +faststart output.m4a# Any audio to WAV (16-bit PCM)ffmpeg -i input.mp3 -vn -c:a pcm_s16le output.wav# Any audio to FLACffmpeg -i input.wav -vn -c:a flac -compression_level 5 output.flac# Any audio to OPUSffmpeg -i input.mp3 -vn -c:a libopus -b:a 96k output.opus# Video file to MP3 (extract audio)ffmpeg -i input.mp4 -vn -c:a libmp3lame -b:a 192k output.mp3
-vn drops any cover art or video stream, which prevents a failure when the input contains an image stream.
-map_metadata 0 keeps title and artist tags where the target supports them.
Cover art is kept as an optional improvement (for MP3 and M4A) once basic conversion is stable.
Behaviours that need care
Voice notes from WhatsApp arrive as OPUS in an OGG container (.opus, .ogg) or sometimes as .m4a or .amr. These are among the highest-demand inputs, so each must be tested.
Sample rate and channels. Keep the source values by default. Offer "mono" and a sample-rate choice later (Phase 2).
Lossy to lossless. Converting MP3 to WAV or FLAC does not restore quality. The page copy says so.
Large WAV and FLAC files can exceed memory limits on phones (section 15).
Progress. FFmpeg reports progress as a fraction based on the input duration; if the duration cannot be read, show an indeterminate bar.
Very short and silent files must succeed.
Multiple audio streams (some video files): use the first audio stream, with a clear note.
Browser alternative for common cases
For tiny files, the browser can decode audio with its built-in audio API and encode WAV by hand, which avoids loading the large engine. This fast path is optional: use it only for WAV output from small files, to speed up the most common request. It is a later optimisation, not a Phase 1 requirement.

Transcode (full path)
Decodes and re-encodes video and audio
The streams are not compatible (for example HEVC or VP9 going to MP4 for wide compatibility; AVI with old codecs)
Slow in WebAssembly, heavy on memory
Decision logic. First, probe the input to find its video and audio codecs. Then, if the codecs are allowed in the target container, remux. Otherwise transcode. Show the user which path is being used ("Fast copy, no quality loss" or "Re-encoding, this may take a while"). A user option lets them force a re-encode.
Probing
Run FFmpeg with the input only and parse the stream information printed in the log (codec names, resolution, frame rate, duration, rotation, audio channels). The probe result drives the path decision, the time estimate and the warnings (for example "4K video, this will be slow on your device").
Command patterns
# Remux to MP4 (fast, no re-encode)ffmpeg -i input.mov -c copy -movflags +faststart output.mp4# Transcode to MP4 (wide compatibility)ffmpeg -i input.mkv -c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p \  -c:a aac -b:a 128k -movflags +faststart output.mp4# Transcode to WebM (VP9 + Opus)ffmpeg -i input.mp4 -c:v libvpx-vp9 -crf 33 -b:v 0 -row-mt 1 -c:a libopus -b:a 96k output.webm# MP4 to GIF (two-pass palette for quality)ffmpeg -i input.mp4 -vf "fps=12,scale=480:-1:flags=lanczos,palettegen" palette.pngffmpeg -i input.mp4 -i palette.png -lavfi "fps=12,scale=480:-1:flags=lanczos[x];[x][1:v]paletteuse" output.gif# GIF to MP4ffmpeg -i input.gif -movflags +faststart -pix_fmt yuv420p -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2" output.mp4# Video to MOVffmpeg -i input.mp4 -c copy output.mov
The encoder names above must exist in the chosen build. In particular, libx264 is licensed under the GPL, so many WebAssembly builds either include it with GPL consequences or leave it out (section 19). The build decision in section 23 settles which encoders are used. If libx264 is not available, the fallback is a build with another H.264 encoder, or the Web Codecs API where the browser provides a hardware encoder.

Behaviours that need care
Even dimensions. H.264 needs even width and height. Add a scale filter that rounds to even numbers for odd sizes.
Rotation metadata. Phone videos store rotation as metadata. Remux preserves it; transcode applies it. Test portrait and landscape files.
HEVC (H.265). iPhones record HEVC by default. Playback of HEVC is not supported everywhere, so "HEVC to H.264" is a core Phase 1 page. FFmpeg's decoder handles it, but 4K HEVC is very slow in WebAssembly; set a size and resolution warning.
HDR and 10-bit. Convert to 8-bit SDR for wide compatibility using tone-mapping filters, or warn that colours may look flat. Recommend a simple default and mark the improved path for Phase 2 (verify).
Variable frame rate from phones: set a constant frame rate with -vsync cfr or -fps_mode cfr (flag name depends on the version) to avoid audio drift.
Subtitles and extra tracks in MKV: copy the first video and audio streams only; ignore the rest with a note.
Interlaced sources (some AVI, MPEG): add a deinterlace filter when the probe reports interlacing.
Fast start. -movflags +faststart moves metadata to the front so MP4 files begin playing quickly on the web.
Duration and progress. Use the probe's duration to compute progress.

12. FFmpeg.wasm Delivery, Hosting and Caching
The FFmpeg engine is the heaviest part of Hurrykit. Its WebAssembly file is roughly 30 MB for the single-thread core (verify the exact size of the chosen version). How it is hosted and loaded decides whether video and audio tools feel fast or broken.
Problem and constraints
Cloudflare Pages' free tier has a per-file size limit of 25 MiB (verify current limit), so the engine file cannot be served from the site itself.
A first visit must not download 30 MB until the user actually needs it.
Repeat visits must not download it again.
The multi-thread core needs cross-origin isolation (special headers), which can break ad scripts and third-party embeds.
Decisions
Topic
Decision
Core variant
Single-thread core by default. It works without special headers and on every browser. Multi-thread is an optional later upgrade for desktop video only.
Where the engine file lives
A separate object storage bucket with a public custom domain or a CDN path (for example R2 behind Cloudflare), not inside the Pages deployment. (Verify free-tier storage, egress and per-object limits before choosing.)
Version pinning
The engine files are versioned by folder name (/ffmpeg/0.12.x/) and the exact URLs are set in one config file.
Integrity
Store a SHA-256 hash of each engine file in the config and verify after download, so a changed file is never executed.
Compression
Serve with Brotli or gzip, which typically cuts the WebAssembly size by more than half; confirm that the storage provider applies it.
Loading trigger
Load only after the user selects a file or presses "Get ready" on a tool page. Optionally preload when the user hovers over the drop zone.
Loading UI
A progress bar that says "Loading the converter (first time only)" with the percentage downloaded.
Caching
Long-lived cache headers (one year, immutable) on versioned engine files, plus the browser's Cache Storage as a second layer, so a repeat visit loads instantly even offline.
CORS
The storage bucket allows cross-origin reads from the site's domain and preview domains only.
Fallback
If the primary location fails, retry from a second mirror (for example a public CDN that hosts the same version) after verifying the hash.
Loading flow
Check whether the engine is in Cache Storage. If yes, load from there.
If no, fetch with a progress stream from the primary URL.
Verify the hash. On a mismatch, discard it and try the mirror.
Save to Cache Storage.
Create a blob URL for the JavaScript and WebAssembly files and pass them to the library's load call.
Mark the engine ready and remember this in memory for the session.
Headers file (concept)
# public/_headers (site)/*  X-Content-Type-Options: nosniff  Referrer-Policy: strict-origin-when-cross-origin  Permissions-Policy: camera=(), microphone=(), geolocation=()/_next/static/*  Cache-Control: public, max-age=31536000, immutable
The pages that use the multi-thread core would additionally need Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (or credentialless). Do not add these to the whole site while ads are planned. Phase 1 does not use them.
Library worker setup
The @ffmpeg/ffmpeg library runs its own worker. Create one FFmpeg instance per engine, call load with the core and WebAssembly URLs, listen to progress and log events, then use writeFile, exec and readFile. To cancel, terminate the instance and create a new one. Keep the instance alive between jobs within a session to avoid reloading, and terminate it after the idle timeout.
Costs and limits to monitor
Storage and download bandwidth of the engine file (every first visit downloads it).
Request and egress limits of the free tier. If they are exceeded, move to a paid storage plan or use the CDN mirror as the primary.
Monthly check: how many visitors load the engine, and the failure rate of the download.

These follow the commonly used Core Web Vitals thresholds. Treat them as goals to test against, not guaranteed results.
Loading strategy
Static HTML with all text content, so the page is useful before any script runs.
The tool's interface hydrates quickly; the engine loads only on demand.
Engine code is split per engine and per codec: for example the HEIC decoder loads only on HEIC pages, and the AVIF encoder only on AVIF output pages.
Preload the engine when the pointer or touch nears the drop zone, or on a "Get ready" tap.
Fonts are self-hosted and limited; images are small, with fixed dimensions.
Third-party scripts (analytics) load late and are tiny. No ad scripts exist in Phase 1.
Memory management
Practice
Detail
Estimate before running
Image: width times height times 4 bytes, times about 2 for working copies. Video: file size times about 3 for transcode. Audio: decoded size depends on duration, sample rate and channels.
Compare to a device budget
Use navigator.deviceMemory (where available), hardware concurrency and the user agent to choose a class (low, mid, high). If a value is unavailable, assume the lower class on mobile.
Warn or block
Warn at the soft limit and block at the hard limit, with an explanation and a suggestion.
Free quickly
Delete engine files, close bitmaps (bitmap.close()), revoke object URLs and clear arrays as soon as a job completes.
One heavy job at a time
Video and large audio jobs run one by one. Image jobs may run two at once on high-class devices.
Terminate on idle
Stop the worker after a short idle period and after errors.
Recover from crashes
If the tab or worker dies, the page shows a message the next time it loads and suggests a smaller file.
Speed practices
Use remux whenever possible for video (section 10).
Use the veryfast encoder preset by default and offer a slower "Smaller file" option.
Use the browser's native image encoder for common formats, which is much faster than WebAssembly.
Offer the multi-thread core as an optional upgrade only after verifying it on target devices.
Show a realistic time estimate and keep the screen on during long jobs using the Screen Wake Lock API where supported.
Warn mobile users that switching apps may pause or kill a long conversion, especially on iOS.
Network considerations
The 30 MB engine file is the largest cost for first-time video and audio users. Say so up front and cache it for future visits.
On metered or slow connections (as reported by the network information API where available), ask before downloading the engine.
Make the experience work offline after the first load for tools whose engine is cached (a bonus, later made into an installable web app).
Measuring
Run a Lighthouse check in CI on the home page and one page of each department, and fail the build when scores fall below the thresholds.
Track real-user timing through the privacy-friendly analytics where supported.
Keep a table of measured results per device in docs/compatibility.md and update the size limits from it.

Implementation
Use a privacy-friendly analytics tool that does not use cookies and does not track people across sites. Custom events are sent through its simple event call.
Error logs go to a tiny endpoint (for example, a serverless function on the host or a free-tier logging service) that accepts only the allowed fields. The endpoint rejects anything with extra fields.

24.3 Format detection (engines/shared/detect.ts)
export async function detectFormat(file: File): Promise<string | null> {  const b = new Uint8Array(await file.slice(0, 32).arrayBuffer());  const ascii = (s: number, e: number) => String.fromCharCode(...b.slice(s, e));  if (b[0] === 0xff && b[1] === 0xd8) return 'jpg';  if (ascii(1, 4) === 'PNG') return 'png';  if (ascii(0, 4) === 'RIFF' && ascii(8, 12) === 'WEBP') return 'webp';  if (ascii(0, 3) === 'GIF') return 'gif';  if (ascii(4, 8) === 'ftyp') {    const brand = ascii(8, 12);    if (['heic', 'heix', 'mif1', 'msf1'].includes(brand)) return 'heic';    if (brand === 'avif') return 'avif';    if (brand === 'qt  ') return 'mov';    if (brand === 'M4A ') return 'm4a';    return 'mp4';  }  if (ascii(0, 4) === 'OggS') return 'ogg';       // may be opus or vorbis: inspect further  if (ascii(0, 3) === 'ID3' || (b[0] === 0xff && (b[1] & 0xe0) === 0xe0)) return 'mp3';  if (ascii(0, 4) === 'fLaC') return 'flac';  if (ascii(0, 4) === 'RIFF' && ascii(8, 12) === 'WAVE') return 'wav';  if (b[0] === 0x1a && b[1] === 0x45 && b[2] === 0xdf && b[3] === 0xa3) return 'mkv'; // also webm  return null; // fall back to the extension, then to "unsupported"}
The real version also needs: AVI, WMV, FLV, 3GP, TIFF, BMP, AMR, AIFF, WMA and the Opus-versus-Vorbis check inside OGG.
